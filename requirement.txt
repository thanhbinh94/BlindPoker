# 1. PRIMARY PRODUCT OBJECTIVE

Build a **real-time online multiplayer poker web application** supporting multiple poker game modes.

The application must support:

### Game Mode A — Normal Poker

Standard poker gameplay following recognized poker rules.

### Game Mode B — Blind Poker

A poker variant inspired by the general gameplay concept of Vietnamese "3 cây":

* Players place a fixed/blind wager before seeing community cards.
* The game has high randomness.
* The winner is still determined according to poker hand-ranking rules.
* The game should support:

  * Blind Poker 2 Cards
  * Blind Poker 3 Cards
* Blind Poker must support AI/bot players.

The product must not involve real-money gambling.

# 7. BLIND POKER

Blind Poker is a distinct ruleset.

It must support:

## 7.1 Blind Poker — 2 Cards

Initial flow:

1. Start round.
2. Deal 2 private cards to each player.
3. Community cards have not yet been revealed.
4. Players place the required fixed/blind wager.
5. Continue according to the defined Blind Poker rules.
6. Reveal community cards according to the selected rules.
7. Complete the hand.
8. Evaluate poker hands.
9. Determine winner.
10. Distribute pot.

---

## 7.2 Blind Poker — 3 Cards

The 3-card variant must be explicitly defined before implementation.

Determine:

* Whether all 3 private cards can be used.
* Whether one card must be discarded.
* Whether the player selects cards.
* How private cards interact with community cards.
* Number of community cards.
* Betting timing.
* Showdown rules.
* Hand evaluation rules.

Do not leave these rules implicit.

The final rules must be documented in the SRS.

Normal Poker should support configurable betting ranges instead of a single fixed wager.

# 67. FINAL OPERATING PRINCIPLE

Treat the project as a real software product.

Think like:

* A Product Manager when defining requirements.
* A Game Designer when defining gameplay.
* A Software Architect when defining system boundaries.
* A Senior Engineer when writing code.
* A QA Engineer when testing.
* A Security Engineer when validating trust boundaries.
* A DevOps Engineer when deploying.

Do not blindly follow ambiguous requirements.

Do not over-engineer.

Do not under-engineer the game integrity.

Prefer:

> **Simple architecture + strong separation of responsibilities + authoritative server + shared game core + independently deployable Normal/Lite editions.**

The most important architectural rule is:

> **Shared Core → Separate Features → Separate Dependencies → Separate Builds**

And the most important maintainability rule is:

> **If a gameplay change requires modifying Normal and Lite separately, reconsider the architecture.**

The final goal is a system that is:

> **Correct, lightweight, realtime, secure enough for its scope, maintainable, easy to deploy, and extensible without unnecessary complexity.**
