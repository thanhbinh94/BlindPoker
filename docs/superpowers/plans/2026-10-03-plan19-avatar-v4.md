Steps use checkbox (`- [ ]`) syntax for tracking. Phases B and C are **controller steps** (the controller drives ChatGPT in the user's Chrome); never hand them to a subagent.

**Goal:** Ship avatar v4 — a player picks gender, hairstyle (per gender), skin tone, hair colour and eye colour separately, and every character stands in one new, relaxed pose with five-fingered hands — with old accounts and saved outfits converted on read, the art redrawn through the registry after a single style gate, and the old flat bases retired at the end.

**Architecture:**
- **Data.** A configuration is `{ v: 4, gender, hairStyle, outfit, skinColor?, hairColor?, eyeColor?, head?, face?, aura?, frame?, title?, badge? }`.
  - `hairStyle` is an item slot drawn on two layers (L20 back, L60 front); 8 free items, each with a `gender`, a `counterpart` and a `naturalColour`.
  - `skinColor` is a colour slot (6 free items) painted through skin masks on the body (L30) and the face (L50).
  - `apps/normal-server/data/avatar-bodies.json` (per gender: body, six faces, natural eye colour) replaces `avatar-bases.json`.
  - The server writes only v4 and repairs everything older **on read**: players and saved outfits, v1/v2 → v3 → v4 (spec §4.5). No SQL migration.
- **Art pipeline.** New kinds: body (`body_<g>_L30`), body faces (`body_<g>_face_<expr>_L50`), hair split front/back (`item_hair_<code>_L20/L60`). Skin masks, checks C12 (the head does not move) and C13 (the hair split), v4 review sheets, and registry kinds/templates so the controller can generate them.
- **Clients.**
  - The kit's `ChibiConfig` becomes body + hair + wearables + three colours.
  - The web maps the v4 API onto it.
  - The wardrobe gains a **Nữ | Nam** switch and the tabs **Kiểu tóc** / **Màu da**.
  - Lite draws its default chibi on the new bodies.
- **Order.** Code on labelled stand-ins (Phase A: A1a–A7) → the style gate, the one stop (Phase B) → art batches (Phase C) → switch-over (Phase D: D1, D2) → merge and deploy. The LAN host keeps the old characters until the merge after Phase D.

**Tech Stack:** TypeScript strict ESM (`.js` imports), React 18.3, CSS modules, Vitest + Testing Library, Playwright 1.62, Fastify 5 + Drizzle (PGlite in tests), Node 22 scripts with `sharp` 0.33 (`apps/normal-web/scripts/avatar-pipeline*`, `avatar-registry*`), Claude in Chrome + ChatGPT (art; controller only).

**Rulings made while writing this plan** (spec vs code; every one is restated in the task it binds):

1. **C12 measures the eyes and the chin, not the skull.**
   - F01/M01's hair is baked into their L30/L50 (`ingest --as base` cuts one flat picture, `extract.mjs` ~1398-1422), so their skull width cannot be measured.
   - C12 compares the new body's eye midpoint, eye span and chin line with F01's measured values instead, each within 2 % of the 208 crop (4.16 frame units).
   - The centroid is taken in frame units as **pixel index / 2 at @2x, with no half-pixel offset**; that is the convention the pinned values were measured with (pre-flight #22).
2. **Both bodies are held to F01's head.** M01's eye line sits 4.6 units lower than F01's (198.6 vs 194.0), which is beyond the tolerance. Every hat, glasses, aura and frame layer was cut on F01 and is shared by both genders.
3. **`hairStyle` is required but is not in `REQUIRED_SLOTS`.**
   - `loadItemCatalog` demands exactly one `isDefault` item per required slot (`items.ts` ~295-299) and refuses `free` together with `isDefault` (~261).
   - All eight hairstyles are free, and the default depends on gender.
   - So `hairStyle` is validated on its own (`HAIR_SLOT`), with defaults in `DEFAULT_HAIR`.
4. **Hair file names get their own pattern.**
   - `item_hair_f_bob01_L60` has a one-letter segment (`f`). `CODE` (`manifest.mjs` ~161) forbids that, so that a trailing `_m` always reads as a per-wear variant.
   - So hair layers have their own name alternative, `item_hair_[fm]_<code>_L(20|60)`, and never take per-wear variants.
5. **Body tint parameters are derived, not written in the JSON.**
   - Spec §4.3 puts `skin/eyes { meanL, files }` in `avatar-bodies.json`. The code's rule is that tint parameters are derived from the manifest (`bases.ts` `deriveTint` ~121-152: "never half-tintable by someone editing JSON").
   - So `BodyDef.tint` is derived at load and served by `/api/catalog/avatar`; the JSON holds the files and the natural eye colour only.
6. **The old bases' natural eye colours are measured and pinned; f03 keeps green; f01/m01 keep their eyes.** No file records the old irises. They were measured from the committed art as the iris colour under each `face_neutral` eye mask:

export function swapGender(config: AvatarConfigDto, gender: Gender, items: ReadonlyMap<string, ItemDto>, owned: ReadonlySet<string>): AvatarConfigDto {
  if (config.gender === gender) return config
  const counterpart = items.get(config.hairStyle)?.counterpart
  const fits = (id: string | undefined): id is string => id !== undefined && items.get(id)?.slot === 'hairStyle' && items.get(id)?.gender === gender && owned.has(id)

  return hairStyle === undefined ? config : { ...config, gender, hairStyle }
}
